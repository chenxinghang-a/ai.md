# SCADA round 175 —— 前后端端口发现契约 + 前端运行时闸门

**版本**：`1.3.1039` → `1.3.1040`（后端 `VERSION` / 前端 `package.json` + `package-lock.json` lockstep）
**日期**：2026-09-24 起，2026-10-07 收尾（中间因 WorkBuddy 安装目录被削、
两个执行通道全挂而中断 —— 见 §13）
**上一轮**：`SCADA-round174-打包产物运行时冒烟-20260924.md`

---

## 1. 一句话结论

上一轮把**后端** CI 的 fail-open 闸门（`test -f <exe>`）改成了真起真跑的冒烟。
本轮顺着同一类空白往下走，落到**前端** `electron-build` job —— 结果在勘察阶段就挖出一个
**从未暴露过的真实缺陷**：

> `electron/main.js` 拼的 `runtime.json` 路径是**错的**。实际发布的 onedir 布局下，
> 后端把端口文件写在 `<backend_dir>/_internal/data/runtime.json`，而前端读
> `<backend_dir>/data/runtime.json`。于是 `readRuntimePort()` **恒返回 null**，
> 整个「避免 5000/5001 错配」的机制**一次也没有生效过**。

它没暴露，只是因为回退值 5000 恰好等于模拟模式端口，而 Electron 又恒 `spawn(exe, [])`
不传参数 → 恒模拟模式。**巧合掩盖了缺陷。**

本轮把它修掉，并补上一道**只有真起服务才能验**的闸门：后端写出的 `runtime.json`，
必须能在**前端自己的口径**上找到。

## 3. 挖出的真实缺陷

### 3.1 证据链（全部实测，非推断）

**后端侧（真源）**：

```
paths.py:20-33   _get_project_root()  → sys.executable 的父目录 = <backend_dir>
paths.py:47-52   _internal/ 存在 → _BASE = <backend_dir>/_internal
paths.py:56      DATA_DIR = _BASE / 'data'
paths.py:64      RUNTIME_JSON_PATH = DATA_DIR / 'runtime.json'
```

⇒ **真实落点 = `<backend_dir>/_internal/data/runtime.json`**

实测真产物（`industrial_scada/dist/scada-backend/`）：

```
_internal/data/runtime.json        存在，132 字节
                                   {"port": 5000, "host": "127.0.0.1",
                                    "pid": 21724, "mode": "simulated", ...}
data/runtime.json                  不存在（该目录下只有 queue/）
```

**前端侧（写错的）**：

```
main.js:25   const RUNTIME_JSON_PATH =
               path.join(path.dirname(getBackendPath()), 'data', 'runtime.json')
main.js:22   注释：「路径与后端 paths.RUNTIME_JSON_PATH 对齐 ——
                    <backend_dir>/data/runtime.json」
```

**`paths.py:62` 的注释也是错的**，原文：「Electron 侧通过 `<backend_dir>/data/runtime.json`
读取（与冻结/开发布局一致）」—— 错误的认知在两侧互相印证，谁也没去实测。

### 3.2 后果链

```
readRuntimePort()              恒 null（路径不存在）
  → syncBackendPort()          永远拿不到真实端口
  → resolveBackendPort()       启动前探测 5000/5001（此时后端还没起）→ 两个都不通
  → 回退 BACKEND_PORT = 5000
  → waitForBackendNonBlocking() 每 1.5s 轮询 5000，60s 后判「后端离线」
```

### 3.3 为什么一直没暴露

| 环节 | 值 | 说明 |
|---|---|---|
| `run.py:446` | 模拟模式 → 5000；真实/模拟器模式 → 5001 | 端口随模式变 |
| `main.js:260` | `spawn(exe, [], ...)` | **恒不传参数** |
| `run.py:107` | 无参数 → `simulation_mode = True` | 恒模拟模式 → 恒 5000 |
| 回退值 | 5000 | **恰好等于**模拟模式端口 |

⇒ 今天能跑，纯属回退值与唯一可达模式的端口撞上了。
一旦（a）前端加了模式切换、（b）`WebConfig.PORT` 改了、或（c）装了真实设备配置，
应用会**永远显示「后端离线」且日志里没有任何异常**。

## 4. 修法 1：把定位口径抽成可测模块

新增 `scada-app/electron/backend-paths.js`（`main.js` 与 CI 闸门**共用同一份实现**）。

原先这段逻辑内联在 `main.js` 里，而 `main.js` 是单体脚本、**不导出任何东西** ——
既无法单测，也无法被闸门复用。抽出来后：

- `getBackendPath({isPackaged, resourcesPath, appDir})`
- `runtimeJsonCandidates(exePath)` → **两个候选，onedir 优先**
  ```js
  [ ['_internal', 'data', 'runtime.json'],   // onedir（当前发布形态）
    ['data', 'runtime.json'] ]               // onefile / 配置目录平铺
  ```
- `findRuntimeJson(exePath)` → 第一个存在的路径（探测，不猜）
- `readRuntimePort(exePath)` → 端口号或 null

**顺序不能反**：onedir 产物里 `<backend_dir>/data/` 也可能存在（历史运行残留），
排前面会读到陈旧的 `runtime.json`。

`main.js` 的改动是外科手术式的：加一个 `require`、把 `getBackendPath()` 与
`readRuntimePort()` 改成委托、删掉写死的 `RUNTIME_JSON_PATH` 常量、把两处错注释改对。

后端侧同步把 `paths.py:62` 与 `run.py:451` 的错注释改对 —— **不能让下一个人继续信它**。

## 5. 修法 2：新闸门 `tools/verify-backend-runtime.js`

Node 实现（前端仓库原生，`tools/*.js` 的既有约定）。判**五件事**：

| # | 判定 | 为什么 |
|---|---|---|
| 1 | 进程**活着** | 缺 `hiddenimports` 的典型症状就是启动即退 |
| 2 | 端口**起来了** | 卡在配置读取 / 依赖加载时端口不会开 |
| 3 | `/api/health/status` 返回 200 且 `success == true` | 接口本身没坏 |
| 4 | 健康判定**无确定负面信号**，且巡检线程**已跑过至少一轮** | 见下 |
| 5 | **前后端契约**：`runtime.json` 能在**前端口径**上找到，且端口与实监听一致 | **本脚本存在的主要理由** |

第 4 条：`/api/health/status` 是**探活**接口，磁盘写满 / 落库停摆时**照样返回 200** ——
只看状态码等于没测。结论在响应体里。而且 `HealthChecker.start_periodic_checks(interval=30)`
是「先 sleep 再跑第一轮」，所以必须等检查项从 `unknown` 变成结论（`resolved`）。
`unknown` 与 `degraded` **不判负** —— 前者是启动瞬态，后者会随 runner 快慢抖动
（`STALE_DEGRADED_SECONDS = 30`，阈值很紧）。**会抖的闸门早晚被人关掉。**

派生字段 `unhealthy_modules` **不采信**，一律从 `modules` 重算。

额外加了两条前置/收尾判定：

- **启动前候选端口必须干净** —— 否则健康响应可能来自外部服务，闸门会以「通过」
  姿态放过一个根本没起来的产物。这是 fail-open 的另一种形态。
- **杀掉进程树后要等端口真正关闭**（不只是等根进程 `exitCode`），并**清理+复核**产物目录。

**刻意没有「跳过」分支**：exe 不存在、进程提前退出、端口不开、非 200、有负面信号、
端口文件找不到、端口不一致、清理有残留 —— 一律 exit 1。

## 6. 修法 3：CI 接线（两道，不是一道）

`scada-app/.github/workflows/ci.yml` 的 `electron-build` job 加两步：

```yaml
# ① 暂存目录（extraResources 的「源」）—— 放在 npm ci / electron-builder 之前，早失败早报
- name: Smoke staged backend (start it, probe health, kill it)
  run: node tools/verify-backend-runtime.js --exe backend/scada-backend.exe

# ② 安装包内（extraResources 的「产物」）—— 放在 Build NSIS installer 之后
- name: Smoke shipped backend (from win-unpacked resources)
  run: node tools/verify-backend-runtime.js --exe release/win-unpacked/resources/backend/scada-backend.exe
```

**② 不是 ① 的重复**。两者之间隔着 electron-builder 的复制 + filter：

- ① 跑的是 `backend/`（源）
- ② 跑的是 `release/win-unpacked/resources/backend/`（真装到用户机器上的那份）

若 `_internal/` 被 filter 漏掉、或 `to:` 路径写错，**源目录照样完好、①照样绿，
而装到用户机器上的那份是坏的**。

在此之前，CI 里**没有任何一步看过 `resources/backend/`**：`verify:dist` 只看 `dist/`，
`verify-asar` 只看 `app.asar` 内的 `dist` 引用。也就是说
**「安装包里的后端能不能跑」从未被自动化验证过**。

另加 `npm run verify:backend-runtime`，本机可一键复现同一道门。

## 7. 修法 4：清理必须「删完再复核」（我自己代码里的缺陷）

**这是本轮第二个真实缺陷，出在我刚写的代码里。**

`backend/` 是 `extraResources` 的源，而 filter 是「全部文件，再排除 `*.log` / `logs` /
`exports` / `__pycache__` / `*.pyc`」—— **`data/` 不在排除列表里**，且 electron-builder
**不看 `.gitignore`**。所以冒烟跑出来的模拟数据库 / `runtime.json` / `logs`
会**原样打进安装包，装到用户机器上**。

第一版清理是「一次性 best-effort」：`unlink` 没抛异常就算成功。

**问题**：Windows 上删除一个仍被句柄占用的文件时，`DeleteFile` 会成功返回，
而目录项要等最后一个句柄关闭才消失 —— **「删了」与「还在」可以同时为真**，
而代码只看「有没有抛异常」，于是**静默放过**。

改成三步：

```js
// 1) 删
cleanupCreated(root, before)
// 2) 复核 —— 这才是判据：按路径集合重算「仍存在的运行期新文件」
runtimeNewFiles(root, before)
// 3) 删 → 复核 → 退避 → 再删（3 次）
cleanupUntilClean(root, before, attempts = 3, delayMs = 500)
```

复核后仍有残留 → **`exit 1`**，并明确打印「这些文件会随安装包发到用户机器上」。
`finally` 里的 `return` 会覆盖 `try` 的返回值 —— 这里**正是要覆盖**：
清理没做干净时，即使健康判定通过也不能算过。

这与 round 174 的教训同源：**没有回头验证的断言等于没有断言。**

**首轮暴露的两个问题，都不是代码缺陷，而是测试自己的问题：**

**① M2 前置对照失败 —— 用例没写显式超时。**
`-t` 模式 `global_status == unhealthy` 匹配到 3 条用例，其中 1 条本来就红。
红的是 smoke 用例「`global_status == unhealthy → exit 1`」：它当时没写显式超时，
用 vitest 默认的 5s，而起进程 + 探活 + 收尾刚好超了。已补 `30000`。

**② M6 没被抓住 —— 测试只断言 exit code，断言不到「失败在正确的地方」。**
把契约判定整体架空（`if (!found)` → `if (false)`）后，代码落到下一条判定
「`runtime.json` 报的端口与实监听不一致」→ `readRuntimePort()` 返回 `null` ≠ 端口
→ **照样返回 1** → 用例照样绿。

修法（已落地）：捕获闸门输出（`vi.spyOn(console, 'error')`），
每条负向用例**额外断言关键原因文本**：

```ts
expect(code).toBe(1)
expect(out).toContain('找不到 runtime.json')   // ← 这一条才是判据
expect(out).toContain('契约破裂')
```

同理给「产物不存在 / 启动即退 / 端口被占 / 非 200 / 非法 JSON / unhealthy /
尚未跑第一轮 / 端口不一致」各加了原因断言。
**闸门有几条失败路径，就要有几条原因断言 —— 否则路径之间会互相掩护。**
（已沉淀为 skill `ci-gate-hardening` 的「守卫 4」。）

**另：三条纯 fs 的清理用例在本机单独跑就要 4.1s**（本机文件系统调用慢），
满载并行时超 vitest 默认 5s → 也补了显式超时。它们不是计时敏感用例。

> **⚠️ 变异台第一版是假绿的，值得单独记一笔。**
> 它用 `execFileSync` 起 vitest，而**本机 node 里所有同步 spawn 都返回 `EBUSY`**
> （连 `cmd.exe` 都起不来）→ 每次「跑」都在 1~3ms 内失败 → 7 组全被当成「红」，
> 打印 `ALL_MUTATIONS_CAUGHT`，**而整个脚本只跑了 0.3 秒**。
> 补上**前置对照**（变异之前该用例必须绿）后立刻暴露：`前置对照失败（3ms）`；
> 再补上**耗时打印**，才一眼看出「0.3 秒跑完 7 组」是假的。
> 改异步 `spawn` 后才是真结果。
> —— 同一个教训第三次出现：**没有正向对照的「全绿」和「全红」都可能是假的。**

### 8.4 顺带修掉的一个本机红灯

`tests/tools/verify-dist.test.ts`（round 172 写的）在本机 **7 条全红**：
它用 `execFileSync` 起被测脚本，而本机同步 spawn 一律 `EBUSY`
→ `run()` 永远返回 `code: -1`。
CI 上 `npm test` 是绿的（CI 无此限制），所以这个红灯只在本地出现。

已改成异步 `spawn`（与 `verify-backend-runtime.test.ts` 同一姿势）。
改完**本机全量套件才第一次真正全绿**。

## 9. 本机环境踩坑（跨项目可复用）

### 9.1 node 里不能用 sync spawn

```js
execFileSync(process.execPath, ['-e', 'console.log(1)'])   // → EBUSY
execSync('npx vitest --version')                           // → EBUSY（cmd.exe 也起不来）
```

异步 `child_process.spawn` **正常**（`smoke()` 用的就是它）。
凡是要在 node 里起子进程的脚本（测试台 / 编排脚本），**必须用异步版本**。

### 9.2 跨命令的文件系统视图不一致

排查过程中一度以为「清理没生效」：闸门跑完，`.env` / `logs/` / `_internal/data/` 仍在，
且闸门自己报告「没有新文件」。

把**重置 → 跑闸门 → 复核**放进**同一条命令**后，三次观测完全自洽：

```
1) 重置        → 2052 个文件（干净基线）
2) 闸门        → PASS
3) 跑完复核    → 2052 个文件，.env / logs / _internal/data 全部已清
```

结论：**跨命令的文件系统观测在本机不可靠**（沙箱对工作区有隔离/叠加）。
判定「某操作有没有生效」时，**必须把操作与复核放在同一次执行里**。

另外 `find | wc -l` 与 node 的 `snapshotTree` 在同一状态下给出过不一致的计数 ——
**量文件数要用与被测代码同一个口径**（这里统一用 node）。

## 10. 残留风险

1. **本地 `release/win-unpacked/` 是 6 月 1 日的陈旧产物**（早于 `runtime.json` 特性），
   闸门对它**判红**了。这是 fail-closed 的正确行为，但意味着
   **CI 上第 ② 道闸门（安装包内后端）只能靠 CI 自己验证**，本机无法预演。
2. 两道闸门各增加 CI 时间约 40~70s（合计约 2 分钟）。可接受。
3. 只覆盖 onedir 布局；`build.py` 的 onefile（`SCADA.exe`）不在 CI 构建。
4. 真实模式（`--real` / `--simulator`）在 Electron 里**不可达**（`main.js:260` 恒不传参数）。
   本轮修好路径推导后，一旦将来加了模式切换，端口发现会正确工作 ——
   但**这条路径本身仍未被任何测试覆盖**（没有对应的 spawn 入口）。
5. 本机 `execSync` 系 EBUSY 会让任何用它写测试台的人踩坑（已记 errors.log）。

## 13. 收尾过程中的一次环境故障（已恢复，记一笔）

本轮代码写完、测试通过、变异验完之后，**两个执行通道同时失效**，收尾被卡了一段时间：

```
Bash      : Top-level not found: ...\Programs\WorkBuddy\resources\vendor\PortableGit\bin
PowerShell: Cannot find module '...\resources\app.asar.unpacked\cli\dist\lazy-lite-wb\3191.374ea005.mjs'
```

**真因**：`C:\Users\cxx\AppData\Local\Programs\WorkBuddy\resources\` 下**只剩 `app.asar`**
—— `vendor/`（Bash 工具的引导依赖）与 `app.asar.unpacked/`（PowerShell 通道的 CLI）
都不见了，是安装目录被削掉一大块（顶层还少了 `resources.pak` / `chrome_*.pak` /
`snapshot_blob.bin` 等）。D 盘有一份**同版本 `37.10.3-24`** 的完整安装
（`D:\workbuddy\`）。

**处置**：没有去动安装目录。把需要的东西列清、给出命令后由主人执行：

```
robocopy "D:\workbuddy" "C:\Users\cxx\AppData\Local\Programs\WorkBuddy" /E /XF WorkBuddyAI.exe app.asar /R:1 /W:1
```

**恢复结果**：`vendor/PortableGit`、`app.asar.unpacked`（62 个 lazy chunk）全部回来，
Bash 通道立即可用。PowerShell 通道仍报同一个错（它要**重启应用**才会重新解析模块路径）。

**这次故障暴露的一个教训**：我唯一的两个执行通道都依赖同一份安装，
**它们同时坏掉时我没有任何自救手段**（文件读写只能传文本，复制不了二进制）。
断线期间只能改用只读工具**人工复核**那个「改完没跑过」的测试文件 ——
逐条比对了断言字串与闸门实际打印的文本。**人工复核有价值，但不能替代执行**：
恢复后第一跑就抓到一条真实失败（见下）。

**恢复后第一跑抓到的问题**（正是「人工复核不替代执行」的证据）：

1. `cleanupCreated 只删本次新建的` **超时**（vitest 默认 5s，本机该用例单独跑就要 4.1s，
   满载并行时必然超）→ 给三条纯 fs 用例补了显式超时。
2. `tests/tools/verify-dist.test.ts` **7 条全红** —— 它用 `execFileSync` 起脚本，
   而本机同步 spawn 一律 `EBUSY` → `run()` 永远返回 `-1`。已改成异步 `spawn`。

**改完之后**：前端全量 **261 passed / 15 files**（这是本机全量套件第一次真正全绿）。
