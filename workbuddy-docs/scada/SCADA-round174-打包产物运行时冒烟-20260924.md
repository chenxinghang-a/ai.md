## 1. 缺陷类别：fail-open 闸门

闸门装了，但它测的性质和「能不能用」无关。

```
test -f dist/scada-backend/scada-backend.exe
```

这条断言的真实含义是「构建产物目录里有这个文件名」。它与下面这些**全部无关**：

- 产物能不能启动；
- 启动后有没有在监听端口；
- 服务能不能对外提供健康接口；
- 核心子系统（采集器 / 数据库 / 设备管理 / 告警）有没有初始化成功。

而 PyInstaller 的失败模式恰好落在这些空白里：

| 失败模式 | 打包阶段 | `test -f` | 进程启动 |
|---|---|---|---|
| 动态导入的模块缺 `hiddenimports` | 不报错 | 通过 | `ModuleNotFoundError` 崩溃 |
| 运行时要读的数据文件没进 `datas` | 不报错 | 通过 | 启动即抛异常 |
| 入口脚本在冻结环境里路径推导错 | 不报错 | 通过 | 卡住 / 崩溃 |

于是「构建成功 + exe 存在 + CI 全绿」和「产物一运行就崩」可以**同时成立**。
这正是 2026-09 那个带缺陷的安装包能漏出去的路径之一。

## 2. 自己发现的第二个坑：只看 HTTP 200 也不够

第一版脚本只判「健康端点返回 200」。实测（本机真产物）确实 200，但响应体是：

```json
{"data": {"checks": {"checks": {
  "collector":      {"last_check": null, "status": "unknown"},
  "data_freshness": {"last_check": null, "status": "unknown"},
  "database":       {"last_check": null, "status": "unknown"},
  "devices":        {"last_check": null, "status": "unknown"},
  "disk":           {"last_check": null, "status": "unknown"},
  "memory":         {"last_check": null, "status": "unknown"}
}}}}
```

`/api/health/status` 的 docstring 写明「供负载均衡器探活」——它是**探活**接口，
不是**就绪**接口：

- 它只在 `HealthChecker` 内部抛异常时才返回 500（`展示层/api/api_health.py:86-88`）；
- 磁盘写满、内存打爆、落库停摆时，各检查项已经是 `unhealthy`，**接口照样 200**；
- 其余两个健康接口（`/status/detail`、`/checks`）都挂了 `@jwt_required`，冒烟拿不到 token。

所以「只看状态码」等于把第 1 节那张表里的空白又留了一遍。
真正的结论在响应体里：`global_status` / `modules` / `checks`。

## 3. 实测：健康字段的时间演化

`HealthChecker.start_periodic_checks(interval=30)`（`run.py:308`）在应用启动时拉起
一个后台线程，**先 `wait(30)` 再跑第一轮**（`core/health_checker.py:303-320`）。
所以检查项有一段「全 `unknown`」的启动瞬态。

两次实测（本机 `dist-scada-1.3.1037/scada-backend/scada-backend.exe`，18,909,643 字节）：

| 时刻 | `modules` | `checks` | `global_status` |
|---|---|---|---|
| t=0s | 4 个全 `initialized` | 6 个全 `unknown` | `healthy` |
| t=25s | 同上 | 同上 | `healthy` |
| **t=30s** | 同上 | **6 个全 `healthy`** | `healthy` |

**关键对照**：把产物内的 `_internal/data/` 改名后重跑（模拟 CI 上的全新空库），
结论**完全相同** —— 模拟设备启动后立刻落库，t=30s 时 `data_freshness` 已经是
`healthy`。所以「要求检查项解析出来」在 CI 上不会抖。

新鲜度阈值（`core/health_checker.py:455-456`）：

```
STALE_DEGRADED_SECONDS  = 30    # 数据超 30s 未更新 → degraded
STALE_UNHEALTHY_SECONDS = 120   # 超 120s → unhealthy
```

阈值很紧（30s）。第一轮巡检落在 t=30s，与 `degraded` 边界几乎重合 ——
所以判定口径**必须容忍 `degraded`**，否则闸门会随 runner 快慢抖动。

### 判定口径（只对确定的负面信号判负）

| 信号 | 处置 | 理由 |
|---|---|---|
| `success != true` / 缺 `data` | **判负** | 接口本身坏了 |
| `global_status == 'unhealthy'` | **判负** | 顶层结论就是结论 |
| `checks.global_status == 'unhealthy'` | **判负** | 巡检线程自己的结论 |
| 任一模块 `error` / `disabled` / `unavailable` | **判负** | 缺 hiddenimport 的典型表现 |
| 任一检查项 `unhealthy` | **判负** | 子系统真挂了 |
| 检查项 `unknown`（巡检未跑第一轮） | 容忍，但要等 | 启动瞬态 |
| 检查项 `degraded`（新鲜度临界） | 容忍 | 会随 runner 抖动 |
| 检查项全部 `unknown` 直到超时 | **判负** | 后台巡检线程没起来 = 产物有问题 |

另外一条口径：**`unhealthy_modules` 这个派生字段不采信**，一律从 `modules` 重算。
一个派生字段写错了，采信它的人就会跟着错。

## 4. 实现

新增 `.github/scripts/smoke_packaged_backend.py`（约 400 行）。

纯函数（可单测）：

| 函数 | 职责 |
|---|---|
| `candidate_ports(raw)` | `"5000,5001"` → `[5000, 5001]`（去重、保序、越界校验） |
| `runtime_json_candidates(exe)` | 列出 `runtime.json` 的两种可能位置（探测，不猜） |
| `read_runtime_port(path)` | 读应用自报的端口；任何异常返回 `None`（辅助手段失败不判死） |
| `tail(text, limit)` | 日志截尾 |
| `find_open_port(ports)` | 端口探测 |
| `http_status(url, timeout)` | GET，返回 `(状态码, 完整响应体)` |
| `assess_health(payload)` | **判定核心**：响应体 → `{ok, reason, global_status, modules, checks, resolved}` |

进程管理：

- `kill_tree(pid)` —— Windows 用 `taskkill /F /T /PID`，POSIX 用 `pkill -P` **加**
  `os.kill(pid, SIGKILL)`。必须整树：PyInstaller 的 exe 会拉起子进程，
  只杀父进程会留下孤儿占端口，让**下一次** CI 跑出莫名其妙的「端口被占」。

CLI：`--exe`（必填）、`--ports`、`--health-path`、`--timeout`（默认 180）、
`--checks-timeout`（默认 150）、`--log-tail`（默认 4000）。

退出码：`0` 通过 / `1` 闸门失败 / `2` 用法错误。

### 自己踩的坑 1：`http_status` 只读 400 字节
第一版写的是 `resp.read(400)`（沿用旧代码），而健康响应体有 ~600 字节 ——
**JSON 被截断，`json.loads` 必然失败**，闸门退化成「响应是不是合法 JSON」的随机测试。
改成整份读回（上限 1 MiB，防异常产物刷爆日志）。
这一条已做成变异 M4 钉住。

### 自己踩的坑 2：冒烟会污染产物目录（改完才发现的第三个问题）

`scada-backend.spec` 的 `datas` **不含 `data/`**（列的是 `run.py` / `模板` / `静态资源` /
`配置` / `core` / `采集层` / `存储层` / `报警层` / `展示层` / `智能层` / `用户层` /
`timeseries` / `tools` / `paths.py` / `config.py`）—— 也就是说
`dist/scada-backend/_internal/data/` 是**纯运行期产物**。

而 CI 的下一步正是 `Upload backend artifact`（`path: dist/scada-backend/`）。
冒烟一跑，产物里就多了：模拟库 `scada_simulated.db`（+ WAL/SHM）、`runtime.json`、
`logs/`。**这些会被原样打包进 artifact。** 本机手动跑还会在
`dist-scada-<版本>/` 里留下垃圾（我这次就是手工把它 `mv` 回去的）。

修：新增 `_snapshot_tree()` + `cleanup_created()` —— 运行前拍一份
`(文件清单, 目录清单)`，`finally` 里删掉**本次新建**的东西（含新建的空目录）。

为什么是「求差」而不是「按名字删 `data/` `logs/`」：
哪天 spec 真的开始随包携带 `data/` 预置内容、或携带一个空目录，
按名字删会把产物自己的东西一起删掉。同理，空目录的清理也**只删本次新建的**
（第一版没做这个区分，会把产物原有的空目录一并删掉）。

实测（真产物）：跑前跑后 `files=2062 dirs=193` **完全一致**，无新增、无丢失，
原有的 `_internal/data/` 仍在。

### 接进 CI

`.github/workflows/ci.yml` 的 `build-backend` job：

```diff
-      - name: Verify entry exe exists
-        shell: bash
-        run: test -f dist/scada-backend/scada-backend.exe
+      - name: Smoke packaged backend (start it, probe health, kill it)
+        run: python .github/scripts/smoke_packaged_backend.py --exe dist/scada-backend/scada-backend.exe
```

位置在 `Build backend` 之后、**`Upload backend artifact` 之前**：
上传了坏产物，闸门再红也晚了。

顺带一个副作用：冒烟步骤排在 `Clean-checkout verification` 之前，
而那一步断言 `git status --porcelain` 为空 —— 于是它**同时**验证了
「产物运行时不会往 git 跟踪的树里写东西」。产物只往 `dist/scada-backend/_internal/`
写（`paths._get_project_root()` 的 frozen 分支），`dist/` 已被 `.gitignore` 覆盖。

## 10. 后端全量套件

| 轮次 | 条件 | 结果 |
|---|---|---|
| 第 1 次 | 删除额度**新鲜**，带 `--cov` | **2537 passed / 0 failed**（700.12s，覆盖率 **58.80%** ≥ 阈值 45%） |
| 第 3 次 | 删除额度**已饱和**（`count=74 > threshold=50`） | 14 failed / 2528 passed —— **14 条全是守卫造成的**，不是代码缺陷 |

### 第 3 次那 14 条拆开看

- **6 条** `tests/test_core_regressions.py::test_*_web_port_*` —— 挂在
  `core/config_validator_startup.py:130` 的 `test_file.unlink()`（**既有代码，与本轮无关**）；
- **8 条** `tests/test_packaged_backend_smoke.py` —— 挂在本轮新增的
  `cleanup_created()` 的 `unlink()` 上；
- 共同根因（报错原文）：

  ```
  [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
  {"count":74,"threshold":50,"scope":"turn","targets":["...logs\\.write_test"],"targetCount":1}
  ```

  本机守卫的删除额度是**按轮累计**的（阈值 50），被
  「全量套件 ×1 + 变异台 ×7 组 + 冒烟脚本若干次」烧光了。
  `count` 已等于/超过 `threshold` → 拒绝的理由是**额度饱和**，不是这次删除可疑。
- **为什么第 1 次能全过**：额度是累计的，第 1 次起手时是新鲜的。
- **CI 上没有这个 guard** → 第 3 次那 14 条在 CI 上不会出现。

### 第 3 次顺带暴露的真实改进点（已修）

守卫在额度饱和时抛的是 **`SystemExit(1)`**，**不是 `OSError`**。
`cleanup_created()` 的 best-effort 兜底只 catch 了 `OSError` → 异常穿出 `smoke()` →
**把一次干净的成功判成崩溃**，8 条冒烟用例连带失败（而不是只红真正依赖删除的那几条）。

改为 `except (OSError, SystemExit)` 之后（本机实测，额度仍饱和）：

```
3 failed, 66 passed
[WARN] 产物目录里有 3 个运行期文件未能清理（可能仍被占用）:
       ['logs\\backend.log', 'data\\scada_simulated.db', 'runtime.json']
```

- 8 条 → **3 条**（只剩真正依赖删除的那 3 条）；
- 冒烟不再崩溃，而是打出 WARN 并**保留健康判定结论**。

⚠️ 捕获 `SystemExit` **不是绕过安全控制** —— 文件确实没有被删掉，只是记进
`failed` 由调用方打 WARN。已加单测
`test_guard_systemexit_is_recorded_not_propagated` 钉住这个行为。

### 本机环境说明（已写进测试文件 docstring）

额度新鲜时 `tests/test_packaged_backend_smoke.py` **69 条全过**（实测）。
同一个 turn 里反复跑全量套件 / 变异台之后，**真正依赖删除的 3 条**会红 ——
报错含 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 即为此情形。
排查与规避见 skill `safe-delete-guard-workarounds` §6b（本轮新增）。
