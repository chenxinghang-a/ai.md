## 最终正解（2026-08-16 深夜，用户实测确认生效）
- ❌ 早前结论"直连 11434 无需代理"是**错的**。用户实测：沉浸式翻译直连 11434 仍报"网络连接失败"，改用 11437 桥后立刻正常。
- ✅ 真正根因：沉浸式翻译的 OpenAI 客户端请求带自定义头（authorization / openai-beta / x-stainless-* 等）且以凭据模式发，触发浏览器 CORS 预检(OPTIONS)。Ollama 即便 `OLLAMA_ORIGINS=*`，其预检响应 `Access-Control-Allow-Headers` 也不是 `*`，预检不过→浏览器拦掉实际请求→扩展报"网络连接失败"。
- 证据：浏览器地址栏直访 `http://127.0.0.1:11434/v1/chat/completions` 返回 **405 Method Not Allowed**——证明浏览器能连本机（非 V2RayN 拦 localhost），只是 GET 不被该 POST 接口接受。连通性没问题，问题在扩展 fetch 的 CORS 预检。
- ✅ 修法：`D:\AI\ollama-cors-bridge.py` 监听 **11437**，回 `Access-Control-Allow-Headers: *` 并反射 Origin/允许凭据，转发到 11434；上游用 `ProxyHandler({})` 强制直连，不被 V2RayN 拐走。实测桥通后扩展"测试服务"通过、字幕翻译正常。
- **实测预检(OPTIONS)头对比（2026-08-16 下午，决定性证据）**：
  - **11434（Ollama 本体）**：`Access-Control-Allow-Origin: *`、`Access-Control-Allow-Headers: <固定清单>`（仅 Authorization/Content-Type/Openai-Beta/X-Stainless-* 等枚举、**不是** `*`）、`Access-Control-Allow-Credentials: <空>`。
  - **11437（桥）**：`Access-Control-Allow-Origin: <回显具体源>`、`Access-Control-Allow-Headers: *`、`Access-Control-Allow-Credentials: true`。
  - 结论：11434 失败 = 固定头清单挡不住 SDK 更新新增的 `X-Stainless-*` 头 + 缺 ACAC 与凭据模式冲突；桥用 `ACAH:*`+`ACAC:true`+回显源全覆盖。这解释了"别人能直连 11434、你不行"——别人插件请求恰好契合 Ollama 固定清单且非凭据模式。
- ⚠️ 结论修正：对沉浸式翻译这类 OpenAI 客户端，`OLLAMA_ORIGINS=*` **不够**，本地 CORS 桥是真实必需，不是"多此一举"（与早前误判相反）。
- 交付：`D:\AI\wake-translate.bat` + 桌面 `唤醒翻译.bat`：双击起 Ollama(若没跑)+重启桥(11437)+开 YouTube；**不自动开机**，关闭窗口即停桥。
- 沉浸式翻译填：`http://127.0.0.1:11437/v1/chat/completions` / 模型 `qwen2.5:1.5b` / Key `ollama`。
- Ollama 仍开机自启（HKCU Run + 启动文件夹），但桥不自启，故开机后需先双击唤醒器。
