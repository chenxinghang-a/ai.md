## YouTube 双语字幕油猴脚本（完成）

主人需求：YouTube 视频字幕翻译要精准+不卡+双语字幕；沉浸式翻译插件有 3s 流式翻译延迟（结构性硬伤）；不想被 Pro 订阅卡额度。

方案：油猴脚本路线（Tampermonkey UserScript）。

技术核心：
- 利用 YouTube 全局变量 `ytInitialPlayerResponse.captions.playerCaptionsTracklistRenderer.captionTracks[].baseUrl`
- 同一个 baseUrl 加 `&fmt=json3` 拿原字幕，再加 `&tlang=zh-CN` 拿 YouTube 翻译字幕（谷歌翻译内核，零额度）
- 按时间戳合并双语 → 注入 `#movie_player` 自建 overlay → 二分查找 currentTime 渲染
- fallback：tlang 不可用时调 `translate.googleapis.com/translate_a/single?client=gtx`（免费、不需 key），每 8 条休 1.5s 防 429
- localStorage 缓存（key=`ytbi_<videoId>`），同一视频重看零延迟零请求

产物：
- `yt-bilingual-subtitle.user.js` (10KB)
- `README.md` (使用说明+原理图+路线对比)

快捷键：Ctrl+B 切换显示

未来扩展点（如主人提）：
- 可加百度翻译 API key 选项（百度开放平台免费 10 万字符/月，需要 AppID+Secret）
- 可加导出双语 SRT 功能（已有 events 数据，合并后按 SRT 格式输出）
- 可加多源语言切换 UI（SRC 写死 'en'，但其他语言视频也得支持）

学到的事实（持久记录）：
- YouTube 自带 `&tlang=<lang>` 参数能直接返回翻译后的字幕，无需自己调外部翻译 API，质量同谷歌翻译
- YouTube 字幕 baseUrl 6 小时签名失效，不能长期缓存 URL（但可以缓存翻译后的文本）
- `client=gtx` 谷歌翻译免费接口 2026 年仍可用，但需限流（4-5 秒间隔最稳）
- YouTube 是 SPA，需要监听 `yt-navigate-finish` 事件重新初始化

## 沉浸式翻译接本地 Ollama 关键坑（实测确认，重要！）

主人按之前给的字段填（Key=ollama）后报「网络连接失败」。逐层排查定位根因：
- 浏览器地址栏直开 `http://127.0.0.1:11434/api/tags` 返回正常 JSON → 本地 Ollama 与浏览器到本地连接本身没问题。
- 但沉浸式翻译扩展发请求带 `Api-Key` 自定义头；**Ollama 的 CORS 预检 `Access-Control-Allow-Headers` 不含 `api-key`**（实测 0.32.13 仅含 Authorization,Content-Type,User-Agent,...）→ 浏览器在 preflight 阶段直接拦截 → 报「网络连接失败」。`Authorization` 头在允许列表内，所以无 key 时可通过。
- 之前让填 `APIKEY: ollama` 是错的（触发了 Api-Key 头）。这是判断失误。

**正确配置（沉浸式翻译自定义 AI）**：API 接口地址 `http://127.0.0.1:11434/v1/chat/completions`、**API Key 留空**、模型 `qwen3:4b`、系统提示词保持默认。点「测试服务」即直连成功。

兜底：若某版本沉浸式翻译强制 API Key 必填（不让空），则改用本地代理（监听另一端口吞掉 Api-Key 头再转发 Ollama）或换 yt-subtitle-translator / YouTube 字幕翻译等真正浏览器直连本地的插件。

## 实测推翻前结论：qwen3 think 控制失效 + 代理方案落地（重要！）

之前以为 `qwen3:4b` 可直接当翻译器，实测推翻：
- **`/v1/chat/completions` 的 `think` 参数对本环境（Ollama 0.32.13 + qwen3:4b Q4_K_M）完全无效**：带 `think:false` 反而 completion_tokens=3888（异常高、内容错）；prompt 末尾 `/no_think` 被当成要翻译的文本输出。
- **`/api/chat` 带 `think:false`**：`has_reasoning=False` 但 content 变英文 CoT（"Okay, so I need to translate..."），译文错。
- 结论：**qwen3:4b 在此环境不适合直接做翻译**（快不了、易污染）。

**修正方案**：改用无 thinking 模式的 **`qwen2.5:7b`**（qwen 家族，翻译质量好、不吐垃圾、快），已 `ollama pull qwen2.5:7b`（后台拉取中）。

**落地本地代理 `D:\AI\ollama-proxy.py`（端口 11435）**：
- 自己返回宽松 CORS 预检（`Access-Control-Allow-Headers: *`，含 `api-key`）→ **这才是"Key 留空也失败"的真凶**：沉浸式翻译即使 Key 空也可能发 `Api-Key` 头，Ollama 直连预检不含该头被拦；经代理（预检允许 *）通过。
- 转发到 `http://127.0.0.1:11434`，剥多余头；实测通道通（`translategemma:4b` 经 11435 返回 `你好！`）。
- 注意：qwen3 的 think 控制不可靠，故代理**不再注入 think**，翻译统一走无思考的 qwen2.5。

**插件最终配置（沉浸式翻译自定义 AI）**：
- 自定义 API 接口地址：`http://127.0.0.1:11435/v1/chat/completions`
- API Key：留空
- 模型：`qwen2.5:7b`（拉完；拉取期间可临时填 `translategemma:4b` 验证通道）
- 系统提示词：默认

**若 11435 仍报"网络连接失败"** → 坐实 V2RayN 系统代理把 localhost 也拐走（地址栏能开是因导航层强制绕过 localhost，扩展请求走代理）。解法：退出 V2RayN 临时验证，或 V2RayN 设置把 `127.0.0.1`/`localhost` 加进直连/绕过列表。

注意：代理（11435）与 chat 服务（8765）都是后台进程，可能被回收；要常驻需做开机自启（写注册表）。
